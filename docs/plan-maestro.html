La base es tu visor actual. El crecimiento se organiza en dos experiencias que comparten proyectos, activos y administración.

Recorridos 360, modelo BIM, arquitectura, estructura, instalaciones y secuencia de obra. Para revisión y colaboración con acceso autorizado.

Showroom comercial

Una web de proyecto con recorridos, oferta, planos, variantes y contacto. Para clientes, compradores, inversionistas y asesores.

Un mismo proyecto puede tener ambas experiencias. Cada publicación define qué contenido y datos puede ver su audiencia.

Cómo se reconoce el éxito

  • Publicas proyectos sin reconstruir una página cada vez.
  • El equipo entiende MEP y etapas desde el navegador.
  • Un visitante comprende la oferta desde su celular y contacta con contexto.
  • Actualizar un modelo no rompe recorridos ni publicaciones anteriores.

Cómo limitamos el primer alcance

Primero un flujo completo de publicación y dos proyectos de prueba: uno grande y otro pequeño. Después ampliamos automatización, empresas y experiencias premium.

Supuestos iniciales: producto web, Supabase como base aprovechable y preservación de enlaces actuales. La tecnología final se confirma durante la organización del proyecto.

“Dos ramas” describe el producto. Recomiendo un repositorio con módulos separados al inicio. Las ramas de Git se usarán para cambios y entregas; mantener dos líneas de desarrollo permanentes duplicaría correcciones y administración.

La versión local y GitHub no están sincronizadas

La raíz de Agel/main contiene index.html de 297,884 bytes. El adjunto tiene 319,757 bytes y 6,239 líneas. El contenido de GitHub coincide con la copia existente en esta carpeta; los dos archivos tienen huellas diferentes.

En GitHub todavía aparecen dos declaraciones de hsmSave(); el adjunto contiene una. La conversación previa también deja fundidos y carga progresiva como pendientes, aunque el adjunto ya incorpora partes de ambos. El archivo recibido será la base candidata para comparar y consolidar, antes de reemplazar la versión publicada.

Por verificar, no por asumir: no encontré un flujo de autenticación ni un adaptador Navisworks en el HTML revisado. Tampoco una integración WebXR. El nombre “VR” o un iframe no acreditan esas capacidades. No se revisaron políticas remotas ni se ejecutaron cambios sobre Supabase.

La base segura va primero

P0 · antes de abrir a clientes

Aprovechar las correcciones de Claude, verificar su alcance y cerrar los permisos sobre datos y publicaciones.

Precisiones a la conversación anterior

  • La clave anon/publicable puede ser pública. Los permisos los determinan autenticación, políticas y privilegios. Una clave secreta o service role sí debe permanecer en servidor.
  • Un bucket público permite descargar por URL. No demuestra escritura ni borrado públicos.
  • Un error al borrar una ruta inexistente no prueba seguridad. La validación necesita políticas revisadas y archivos de prueba controlados.

Lo que sí debemos corregir o comprobar

  • Roles por organización y proyecto; autenticarse no debe dar acceso a todos los clientes.
  • Validar estructura, tipos, límites y URLs del JSON cargado por enlace.
  • Texto mediante textContent; HTML permitido solo con sanitización contextual.
  • Separar contenido ejecutable, medios públicos y archivos técnicos privados.

Base documental: seguridad de datos, buckets públicos/privados y control de Storage.

Conservar y unificar el 360

Extraer un PanoEngine compartido por editor y visor público: cámara, carga, transición, hotspots y liberación de recursos. Separar el motor de los controles evita corregir dos implementaciones divergentes.

Revisar la precarga de todas las escenas en vmPreloadAll() (L4139), la llegada de respuestas después de cambiar de escena y el límite de textura por dispositivo. El aviso actual de textura demasiado grande no sustituye entregar una resolución compatible.

Navisworks: publicación primero, automatización después

  1. CoordinarModelo y disciplinas en Navisworks
  2. PublicarNWD con versión identificada
  3. PrepararAPS Model Derivative / SVF2
  4. RevisarVisor APS dentro de AgelArq

La ruta recomendada para probar NWD es Autodesk Platform Services. NWF guarda referencias y no contiene la geometría; no lo trataremos como archivo autocontenido. El soporte del formato y sus versiones se comprobará con una muestra real. [Formatos Navisworks · Model Derivative]

MEP necesita información clasificada

Definir disciplina, sistema, nivel, zona, categoría e identificador de origen. Cuando falten propiedades, usar reglas revisables por archivo o conjunto. La app debe señalar “sin clasificar” en lugar de inventar un sistema. La geometría comercial optimizada y el modelo técnico conservan fines distintos.

360 y 3D se preparan de forma diferente

El 360 permite mirar desde puntos renderizados o fotografiados. Para caminar libremente o cambiar materiales con libertad se necesita geometría y una experiencia 3D preparada. En panoramas, las variantes normalmente requieren renders alternativos alineados. Para productos se puede evaluar model-viewer; para espacios complejos, un motor 3D dedicado.

Calidad profesional del contenido

Definir iluminación, altura de cámara, orientación, continuidad entre escenas y criterio de acabados. Guardar archivos maestros aparte de derivados web. Cada tour lleva plano de orientación, nombres comprensibles y hotspots con propósito. Una publicación comercial requiere aprobación de imágenes, textos y datos de oferta.

Primera versión comercial: captar y dar seguimiento a solicitudes. Reserva con pagos, inventario transaccional y contratos se consideran una fase independiente cuando el proceso de venta esté definido. El clic a WhatsApp no confirma que se haya recibido o atendido un prospecto.

Interfaz entre módulos

El catálogo decide qué mostrar; cada visor recibe activos autorizados, ubicación inicial y opciones. Devuelve eventos de selección o navegación. Las reglas de negocio permanecen fuera del motor: sustituir una tecnología visual no debe exigir rehacer precios, publicaciones o permisos.

Migración sin perder proyectos ni enlaces

  1. Inventariar datos en cada navegador usado, configuraciones compartidas y objetos de Storage. Lo que solo está en localStorage no aparece mágicamente en GitHub.
  2. Exportar respaldo y revisar dependencias; las URLs blob: son temporales y no sirven como almacenamiento permanente.
  3. Importar con identificadores propios, esquema versionado y validación. Registrar faltantes y conservar la copia original.
  4. Mantener lectores de enlaces antiguos y una tabla de correspondencia a las nuevas publicaciones.
  5. Verificar una muestra completa antes de cambiar dominio o punto de entrada. Mantener reversión.

Ciclo de un activo

Carga autorizada → validación → procesamiento → revisión → publicación → distribución → actualización o archivo.

Procesar una fuente una vez por versión/configuración y reutilizar derivados. Ante fallos, mostrar estado y permitir reintentar. Medios públicos se distribuyen por CDN; contenido técnico privado requiere entrega controlada.

  3. Preparar ejecución local, formato, dependencias fijadas y documentación mínima.
  4. Crear entorno de pruebas independiente de producción y datos de muestra.
  5. Registrar configuración pública y secretos de servidor por separado. Un archivo de variables no convierte una variable de navegador en secreta.
  6. Añadir revisiones automáticas pertinentes: sintaxis/compilación, enlaces y recorridos críticos; pruebas de permisos cuando existan.
  7. Publicar una vista previa por cambio y revisar antes de integrar en main.
  8. Comprobar despliegue y reversión antes de sustituir el punto de entrada de clientes.

    domain/           proyectos, escenas y publicaciones

  services/           procesamiento e integraciones
  supabase/           migraciones y políticas versionadas

Esta es una estructura de destino. Empezaremos separando responsabilidades dentro del proyecto existente; las carpetas adicionales aparecen cuando haya código que las justifique. Una plataforma de alojamiento estático puede servir el showroom, pero el editor, permisos y procesos necesitan sus servicios correspondientes.

Flujo de trabajo propuesto: rama corta por cambio → revisión y comprobaciones → vista previa → integración → publicación verificada. El plan HTML se incorpora después a docs/ cuando organicemos el repositorio. Esta entrega no ha creado ramas ni enviado cambios a GitHub.

Objetivos medibles de rendimiento

Para la página comercial: LCP ≤ 2.5 s, INP ≤ 200 ms y CLS ≤ 0.1 en el percentil 75 de visitas. El visor requiere medidas propias: tiempo hasta primera vista útil, tiempo hasta interacción, bytes transferidos y memoria. Son objetivos del plan; todavía no son resultados medidos de AgelArq. Accesibilidad y recuperación

Lista de ambientes alternativa al panorama, información esencial fuera del lienzo, controles con teclado, foco visible y formularios con etiquetas. Ante una falla visual, mantener ficha, planos y contacto. La comprobación automática se complementa con recorridos manuales representativos.

Qué presupuestar

  • Captura o renderizado, preparación de modelos y revisiones editoriales.
  • Almacenamiento de originales y derivados, descargas y alojamiento.
  • Conversiones Autodesk y consultas según tarifa y cuenta vigente.
  • Usuarios, soporte, monitoreo, respaldos y mantenimiento.
  • GPU y transmisión solo si se ofrece renderizado remoto.

Costo mensual de operación = plataforma + archivos/entrega + conversiones + monitoreo/soporte + servicios premium utilizados. La producción visual inicial y sus revisiones se presupuestan aparte. Calcular costo por publicación, actualización y visita con los pilotos.

APS tiene opciones gratuitas con límites y opciones pagadas. No se fija precio ni presupuesto aquí: faltan tamaño de modelos, frecuencia de versiones, visitas, plan Supabase y país/modalidad de facturación. [Opciones oficiales APS]

Indicadores útiles

Tiempo para publicar un proyecto, errores de carga, solicitudes recibidas por visita, solicitudes atendidas, costo de actualización y costo operativo por proyecto. Para BIM: propiedades faltantes, referencias que cambian y tiempo de revisión. Fijar metas después de obtener una línea base.

Servicio continuo

Responsable de precios y disponibilidad, procedimiento de actualización, alertas de cuota/conversión, registro de fallos, restauración y exportación. Definir tratamiento de contactos y condiciones de servicio al concretar el mercado y proceso comercial.
